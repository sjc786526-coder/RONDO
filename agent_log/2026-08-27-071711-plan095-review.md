## 1. 结论

**当前提交验收不通过，任务目标失败；允许按本报告做窄修后重新验收。**

整体架构方向正确：云端 scorer 是既有 service 的兄弟 backend，独立 launcher 形成结构性的 default-off；现有
`PublicationScorer`、service 核心、packet/render、`team_publish` 和本地 worker 没有被改写。严格单标量投影、typed failure、
loopback/HTTPS 边界、非 2xx 正文丢弃、响应上限和普通日志去正文也基本合理。真实 DeepSeek smoke 使用的正式 descriptor 恰好让请求
model 与声明 model 同名，因此已取得的真实 `PASS`/`REWRITE`/HTTP 400 证据本身不因下述通用配置缺口作废。

但当前描述符允许“请求模型 A、声明模型 B”并把 A 的结果静默标成 B，直接违反本任务的 identity 诚实原则；另有 retry 预算、云端在途
取消/关闭证据和 Bazel lock 门禁未闭合。现有 `54/54` 绿灯没有覆盖这些反例，不能据此通过验收。

## 2. Findings

### High：provider 请求模型没有绑定到声明的 model identity

- `cloud_config.rs:163-174,319-341` 分别验证 provider 和 service identity，但没有交叉检查
  `provider.model == service_descriptor.identity.model.model.name()`；model identity 的 revision 也没有与 provider 能证明的事实绑定。
- `cloud_scorer.rs:83-91,153-156` 实际请求 `provider.model`，但 `:217-223` 在 `echoed` 与 `provider_managed` 两种模式下均可能返回
  descriptor 预先声明的 `self.model`。因此可请求 A、声明 B，provider 回显 A 后 service 仍按 B 通过 expected identity equality。
- 当前 `provider_managed_model_identity(model, revision)` 的 `revision` 是自由字符串，而 provider 请求没有 revision 字段；正式值
  `reference` 也不是明确的 `unverifiable/provider-managed` serving revision 标记。

返修必须在启动前把 requested model 与 expected model identity 绑定，并让无法验证的 serving revision 明确表达不可验证语义；补充错绑
descriptor 的反例测试。预计可只改 cloud descriptor/config，不需要扩大 `ServiceIdentity`、wire 或 service 核心；若执行者证明必须改变这些
公共合同，才按 ExecPlan 使用 queue 请示。

### Medium：retry 最坏预算公式少算递增 backoff

- `cloud_config.rs:138-143` 按 `timeout × N + backoff × (N-1)` 验证。
- `cloud_scorer.rs:142-147` 实际在第 1、2、3 次失败后分别等待 `backoff × 1/2/3`；N 次尝试的总 backoff 是
  `backoff × N × (N-1) / 2`。N 大于 2 时可接受实际超出声明 job deadline 的配置。
- service 的 deadline 在排队前启动（`service.rs:332-388`），即使修正 backend 预算，排队也可能使外层 `ExecutionTimeout` 先发生；
  agent log、WBS 和 ExecPlan 中“backend deadline 总先于 service deadline”的表述过满。

返修可选择正确计算三角和，或把运行时退避改为固定值；只需保证校验与实际一致并补 N=3/4 边界测试。现有 service 外层 deadline 保持不动，
无需为了固定 typed failure 而改 service。

### Medium：cloud-specific 生命周期证据没有覆盖真正的在途取消和 active shutdown

- `tests/cloud_process.rs:630-682` 的 cancellation token 在调用前已经 cancel，只证明快捷路径，没有证明 HTTP 请求已经到达 provider 后，
  取消会丢弃 request/retry future、停止后续重试并释放执行资源。
- cloud 集成测试中的 shutdown 都发生在请求完成之后；没有覆盖 active request 下 graceful deadline 后 force-cancel 的有界退出。
- 既有通用 service 测试已经覆盖 queued cancel、job timeout 和 forced shutdown 核心，不需要复制整套平台；但 cloud backend 独有的
  reqwest/retry future 仍需一条真实在途取消和一条 active shutdown 证据。

返修应复用现有 delayed loopback fixture：等待 provider 确认收到请求后再取消，断言无额外 retry 且下一请求健康；再验证 active request
下 shutdown/force-cancel 有界退出且没有后台请求继续。无需新增审计、trace 或测试框架。

### Medium：Cargo 依赖变化后没有闭合 Bazel lock 门禁

`publication-critic/Cargo.toml` 与 workspace `Cargo.lock` 已改变，而 `MODULE.bazel.lock` 没有刷新或通过 lock check。
`multidev/AGENTS.md` 明确要求依赖变化后运行 `just bazel-lock-update` 并提交结果；`MODULE.bazel` 又把 `Cargo.lock` 作为 crate extension 输入，
“依赖 crate 已经存在”不能证明直接依赖边、新 binary 和测试元数据无漂移。

返修必须在具备 Bazel 的环境运行现有 update/check 入口并记录真实结果。允许下载任务局部的 Bazel/Bazelisk 依赖，但不得修改全局工具链；不要求
扩大为 Bazel 全 workspace 测试。

### Low：测试数量记录不准确

新增文件静态枚举为 cloud config 8 项 + template 3 项，共 11 项单测；`cloud_process.rs` 为 9 项集成测试。执行日志、ExecPlan 和
`WBS-COMPLETED` 目前写成“10 单测 + 8 集成”，应按实际数量更正。总门禁 `54/54` 本身正确。

### Low：5 USD 的保守费用推导需按实际 provider 请求重新核对

当前日志把 commissioning/clean smoke 等阶段各算一个事件，但 clean smoke 本身已有两个可能计费请求；首次/第二次 commissioning 也可能
各含多个请求。按用户的保守口径，应以实际可能计费的 provider HTTP request/attempt 计数；无法恢复精确数时采用诚实的保守上界。
该修正只影响费用记录，现有证据表明仍远低于 50 USD，不需要再次调用真实 API。

## 4. 替用户作出的决策

1. **接受独立 cloud service binary 的选择路线。** 它与现有 endpoint + expected descriptor 接缝契合，不要求改 `codex-core` 或增加
   产品 backend 开关。
2. **接受 backend 自身 timeout 作为 service 外层 deadline 内的第一层收敛手段，但不冻结 failure 必须是哪一种。** 修正预算后，立即执行
   的请求通常可先得到 typed backend failure；排队或外层取消时 service timeout/shutdown 可以先发生。文档必须按此准确表达。
3. **不要求复制 Plan 055 全部测试。** 既有通用 queued cancel/job-timeout/forced-shutdown 测试继续作为 service 核心证据；只补 cloud
   独有的 in-flight HTTP cancel 与 active shutdown/force-cancel 两个高价值场景。
4. **Bazel lock 必须闭合，但不要求安装全局工具或运行 Bazel 全 workspace。** 使用任务局部工具完成既有 lock update/check 即可。
5. **不要求重新付费跑真实 API。** 如果返修只涉及 descriptor 交叉校验、诚实 revision、retry 预算、fake 生命周期测试、Bazel lock 和
   文档，且没有改变正式 descriptor 的请求 model、cloud prompt、request/response wire 或 scalar 投影，现有 clean real smoke 可继续作为
   真实证据；若返修改变这些真实调用语义，再按剩余预算判断是否只补一轮最小 smoke。
6. **费用按实际可能计费请求重算，不新增预算设施。** 只需在既有日志中给出精确计数或保守上界。
