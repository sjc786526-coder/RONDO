## 阶段二前必须窄修

### 1. 候选 LoRA 目标会命中 vision tower

`recipe-candidate-v1.json` 用七个通用模块后缀作 `target_modules`，同时把 `vision_tower` 与
`multi_modal_projector` 作为列表式 `exclude_modules`。PEFT 0.19.1 对列表排除只做完整名称或后缀匹配，并不会因为模块
路径中间含有 `vision_tower` 就排除其 `q/k/v/o/gate/up/down_proj` 后代；Pixtral vision tower 确实具有同名投影。
因此 `get_peft_model()` 会产生视觉塔 LoRA，随后现有 `lora_trainable_scope_invalid` 检查会正确中止，但 optimizer step
不会发生并会浪费一次云端加载。

最小修复：把候选 target 改成只匹配 `language_model.layers` 下 attention/MLP 七类投影的正则，保留现有运行时
trainable-scope 检查；增加一个仅用代表性模块名、无需权重的测试，证明语言层命中且 vision/projector 不命中。随后重建
bundle/tar、复核 census 保持不变并重跑 focused tests。依据见 PEFT 0.19.1 的
[`exclude_modules` 语义](https://github.com/huggingface/peft/blob/v0.19.1/src/peft/tuners/lora/config.py#L305-L317)
和 Transformers 5.14.1 的
[`PixtralAttention` / `PixtralMLP`](https://github.com/huggingface/transformers/blob/v5.14.1/src/transformers/models/pixtral/modeling_pixtral.py#L1457-L1577)。

### 2. pair receipt 尚不能证明正式训练与冻结公平合同

`build_pair_receipt()` 会哈希训练 receipt 文件，但只要求它是 canonical JSON；测试中的
`{"status":"completed","steps":2}` 也能作为微调 provenance。runtime/template/request 只接受调用方填写的 64 位 hex，
sampling 也只检查类型和正数，所以并未机械绑定计划要求的 b10333、12,288 / 512、temperature 0、top-p 1、seed 42。
这会让形式上的正式导入在实际工件或公平合同不成立时仍通过。

最小修复：

- pair builder 必须读取并验证 Plan 037 的 **formal completed** training receipt，至少绑定固定 base revision、470 条 train、
  正式 run kind、adapter 身份和 completed 状态；fixture 不得再用任意小 JSON 代替。
- runtime lock、chat template、request contract 和 output contract 由实际普通文件/冻结 lock 计算哈希后写入 receipt，不能由
  调用者裸传 digest；sampling 精确要求 `{12288, 512, 0, 1, 42}`。
- 保持当前轻量 `IdentitySource`/manifest 结构即可，不建立签名链、数据库或通用可信平台。

### 3. 悬空 attempt 没有可恢复终态

journal 在调用前 fsync attempt；若进程、连接或宿主在单样本中断，恢复时固定抛
`paired_journal_attempt_without_terminal`，既不能继续，也不能把该次中断如实收敛为终态。130×2 真实推理只能废弃整个
run directory 并重调既有样本，与本任务允许普通故障恢复及“每条样本一个终态”不符。

最小修复：为唯一尾部悬空 attempt 提供一个显式恢复操作，只允许追加 body-free 的 timeout/structured failure 终态并继续，
不得悄悄重调该样本；补一条中断后收敛并继续、且无重复调用的测试。不需要通用事务系统。

### 4. 阶段二实际命令方案没有落盘

execplan 已勾选上传、依赖安装、固定 revision 下载、日志监控、回收和终止可直接操作，但 tracked README 仍只有抽象步骤。
阶段二前补一页精简 runbook：写清现有 ignored bundle 的实际路径与 hash、选定传输方式的具体命令、Pod 内验包和依赖安装、
smoke/formal env 调用、产物下载与逐文件验真、最后终止顺序。命令保留 Pod ID/host/port 等必要占位符即可，不建立新的
controller 框架。

同时修正两个低风险事实：execplan 的完整执行基线应为实际 `7a53a56662904eb43a857b57a90adc8713ff2bda`，而非当前不存在的
