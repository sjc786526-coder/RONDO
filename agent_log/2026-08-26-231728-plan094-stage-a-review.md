## Findings

### High — 5 USD 硬上限没有约束实际计费 segment

`training/publication-critic-plan094/runpod-launch.sh:5-16` 只检查阶段 B 环境门和任意正整数 timeout，随后可启动任意 worker 命令；它既不消费已验证的 task-owned budget snapshot，也不把 segment 时长与 live L40S、卷/container 费率及剩余 headroom 绑定。`plan094_cli.py:299-307` 的预算门只覆盖训练 `start/resume`，没有覆盖 bootstrap、必要模型下载、parameter inventory、commissioning 的其它命令或训练前后的 Pod 空转。与 `runbook.md:29-35` 的“每个动作消费已验证预算快照”不一致，误设过长 timeout 时可越过用户明确授权的 5 USD 硬边界。

整改目标：让每个可能持续计费的 segment 在开始前消费 fresh、task-owned、已验证的预算信息，并按当时核验费率、保守总账、closure reserve 与 action headroom 拒绝过长的 segment；Pod 创建前仍按根规则独立刷新并核对，不把预算职责塞进 `create-runpod-when-ready.py`。可在现有 launch 接缝加薄 gate，也可采用证据更强且同样简单的等价方案；不要求通用费用平台、签名链或自动化账单系统。保留足够终止余量并在 segment 后及时核对/释放 Pod 仍是执行者的 live 操作职责。

### Medium — Plan 090 历史点被错误授予 Plan 094 best 角色

guarded import 的评测 overlay 已正确设置 `source_external=true` 和 `candidate_eligible=false`，但 `plan094_controller.py:602-654` 的 `_roles_after()` 仍对全部结果计算 `checkpoint_backed_best`、`training_best` 和 turning point；首次只有历史 observation 时，`plan094_controller.py:656-670` 又把 `previous_checkpoint_id` 留为 `None`。因此 Plan 090 历史 checkpoint 会同时成为 Plan 094 的 latest/best/training-best，而不是冻结合同规定的 `previous_only_reassess_under_plan094_rubric`，并可能在后续自有 checkpoint 较弱时继续占用 best 角色。

整改目标：角色和 selection 明确区分历史外部点与 Plan 094 自有点；历史点保留为 continuation previous/reassessment 基准，但不参与 Plan 094 material、best、training-best 或自有 turning/candidate 选择。补一条 guarded-import-only 以及首个自有 checkpoint 后的聚焦回归。具体内部结构由执行者自主选择。

### Medium — 仅导入历史 update 时摘要提前声明本任务已训练

`import_plan090_checkpoint()` 在 `plan094_controller.py:222-224` 把 Plan 090 的历史 update receipt 放入通用 `state["updates"]`；`archive_summary()` 在 `plan094_controller.py:1184-1189` 仅以该列表非空生成 `real_training_run=true`。因此 Plan 094 尚未产生任何 task-owned update 时，commissioning/formal 摘要已经会把历史训练冒充为本任务真实训练进度。

整改目标：`real_training_run` 只在至少一个 Plan 094 自有有效 update/checkpoint 已形成后为 true；guarded-import-only 为 false，继续到下一个有效 Route O update 后为 true。可复用上项的外部/自有来源语义，不必新增另一套状态体系。

### Medium — 复用既有 snapshot 时不清除不需要的 Hub 凭据

`training/publication-critic-plan094/runpod-bootstrap.sh:120-139` 只在 exact snapshot 缺失、进入下载分支时清除 `HF_TOKEN`、`HUGGING_FACE_HUB_TOKEN` 和 `HUGGINGFACEHUB_API_TOKEN`。正常复用 Plan 082/087 exact snapshot 的主路径会把这些不需要的变量继续留给后续进程，与 runbook 所述 token 最小化及项目秘密最小注入边界不一致。

整改目标：在 existing/download 分支之前无条件移除不需要的 Hub 凭据；Hub cache/telemetry 等运行变量也保持 task-local。补轻量行为回归覆盖 existing-model 主路径，不需要引入密钥审计设施，也不得读取或打印任何凭据值。
