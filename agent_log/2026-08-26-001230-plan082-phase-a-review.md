## 中等级问题

### 1. BF16 optimizer step 可能完全不改变原参数，却被记为有效更新

- `plan082_adapter.py` 以 BF16 加载全部参数，`apply_update()` 只要求非零梯度 norm，随后即递增 step 并返回成功；没有证明当前 scope
  中至少一个原参数在 optimizer step 后发生实际数值变化。候选 `1e-5` 学习率可能小于 BF16 在常见权重量级的可表示间隔。
- 这会让数值上全 no-op 的训练进入 observation/checkpoint，甚至形成 `VALID_NO_IMPROVEMENT`，不满足“直接更新原模型参数”。
- 修复验收：每次有效 macro update 至少证明一个当前 scope 原参数实际改变，并记录精炼的变化事实；非零梯度但全 scope bit-identical
  必须拒绝。具体精度、master-weight、学习率或其它更优策略由 commissioning 选择，不在此锁死。

### 2. formal finalizer 可认证错误 base 和不存在的候选 checkpoint

- `plan082_formal.py` 只要求 `base` 是 mapping，未核对 exact-base 固定结构及 selection 的 base identity；对 checkpoint 只检查 state 中的
  字符串关系，未核对正式 artifact store 中的存在性和内容身份。
- 已复现两条错误路径：把有效 state 的 base/selection base 改成 commissioning 身份仍得到 `valid_clean_formal_run=true`；把候选
  observation 的 checkpoint ID 改成任意不存在字符串仍可发布为 research candidate。
- 修复验收：复用或提取既有 Plan 081 completed-history/artifact-store 校验，闭合 exact base、完整 observation/checkpoint/latest 关系、
  selection 全字段和候选工件存在/内容身份；不需要另建可信平台。

### 3. 输出冲突在付费训练完成后才失败

- `plan082_cli.py` 在 `run_scheduled()` 之后才 write-exclusive 写 `state_output` 和 recovery receipt。复用 state 路径或预存输出时，更新和
  terminal checkpoint 已完成后才报 `output_already_exists`。
- 正式 namespace 已被消费却缺少 final state/receipt，只能从新空 namespace 重跑，直接浪费付费 GPU。
- 修复验收：在 base observation 或任何 update 前预检本段全部输出不存在、非符号链接且互不别名；runbook 明确 start/resume 使用不同
  segment 输出。冲突回归必须证明零 update 且未创建正式 artifact namespace。

### 4. formal freeze 未绑定完整实际运行环境

- bootstrap 使用 `--system-site-packages`；formal runtime identity 只包含 GPU/CUDA、Torch、Transformers 等部分事实，没有 Python、
  driver/image 和实际安装依赖身份。commissioning 修依赖或更换 Pod/image 后，旧 freeze 仍可能接受漂移环境。
- 修复验收：生成一个小型实际环境 receipt（例如 Python、image/driver/CUDA、实际 installed-distribution freeze 及其 SHA-256），将必要
  身份绑定进 runtime/formal freeze，并在 start/resume 重新计算比较。普通文本 receipt/hash 足够，不建设环境证明系统。

### 5. Pod 释放前的 handoff bootstrap 没有核验真实保留工件

- `create-handoff-bootstrap --objects` 只验证调用者 JSON 的形状并原样接受 path/bytes/SHA；没有从正式 retention 结果和挂载卷内普通文件
  机械生成或复核清单。漏项、旧路径或旧 hash 可在 GPU review 前“成功”，到 0 Pod 下载时才暴露。
- 这与第二阶段验收必须关闭全部 Pod 依赖的要求冲突；卷虽保留，但当前只读、manifest-driven 入口无法自动修复错误 bootstrap。
- 修复验收：增加窄的 cloud-side producer/verifier，从明确 retention roles/artifact manifest 生成并逐普通文件核对 path/size/SHA，且在
  GPU review 前运行。只扫描任务 formal root 的明确 allowlist；补漏项、stale hash、非普通文件负例即可。

### 6. 0 Pod inventory/download 的 runbook 命令当前不可运行

- `runbook.md` 的两条命令直接使用 `python -B -P -m rondo_eval...`，没有显式 `PYTHONPATH` 或含 boto3 的解释器。仓库根实测首条命令
  以 `ModuleNotFoundError: rondo_eval` 失败；system Python 和现有共享 eval venv 均无 boto3。
- Pod 已释放后，这会直接阻断大型资产交接。
- 修复验收：提供并离线 dry-run 一个明确本地入口，显式绑定当前 worktree/source 和一个项目局部、固定 boto3 版本的轻量环境；两条命令
  使用同一环境。不要把凭据写入依赖或命令行，也不要原样调用 Plan 068 旧资源 CLI。

### 7. bootstrap 的 ready receipt 不是稳定单一结果

- `runpod-bootstrap.sh` 的 pip install/check、HF download 和 snapshot verifier 都可写 stdout，最后才打印 ready JSON；若按 runbook 捕获
  stdout，会得到普通文本/多个 JSON，而不是可稳定解析、可重试消费的 receipt。
- 修复验收：把 bootstrap 结果原子写入明确 task-owned receipt（推荐），或隔离所有子命令输出并保证 stdout 恰好一个 ready JSON；覆盖
  成功、失败和相同输入重试。

### 8. validation 的 `training_state_unchanged` 未覆盖参数、buffer 和 RNG

- `_training_state_guard()` 只比较 optimizer state、scheduler、cursor、step 和 train/eval flag；validation forward 原地修改 model
  parameter/buffer 或消费 Python/Torch CPU/CUDA/NumPy RNG 时仍可声明训练状态未变。
- 已用现有 fake adapter 复现 parameter 被修改后 receipt 仍返回 `training_state_unchanged=True`。
- 修复验收：以轻量版本/身份快照覆盖 named parameters、buffers 和上述 RNG，补 parameter、buffer、RNG 漂移负例。无需逐 tensor hash
  或持久审计设施。

### 9. Plan 081 fixture-only claim 可仅靠新增 profile 参数翻转

- 原 `ContinuousTrainingController` 现在可直接传 `_evidence_profile`；继续使用 Plan 081 fake adapter/logits 即可产生自定义 real evidence、
  `real_quality_claim=True` 和 research candidate。
- 这违反“Plan 081 fixture_fake 不得仅靠翻字段冒充真实训练”的明确边界。
- 修复验收：让 Plan 081 具体 controller 固定 fixture profile；参数化能力下沉到内部中性基类/seam，由 Plan 081 与 Plan 082 具体类型各自
  固定 profile，Plan 082 继续强制真实 adapter。补 fake adapter 无法从 Plan 081 构造路径产生真实声明的回归。
