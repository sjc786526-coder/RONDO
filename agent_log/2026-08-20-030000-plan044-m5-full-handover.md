## 1. 这个任务在做什么

RONDO 是我基于冻结的 Codex CLI `v0.147.0` 改的产品，分两条产品线：`mydev/` = RONDO Local，
**`multidev/` = RONDO Multi**（本任务只碰 Multi）。M-5 是 Multi 方向的收口任务，用**真实模型运行**

**两门缺一不可，且从设计上就不主张 Multi 更优、不做统计显著性。** 即使全过，也只能表述为

## 4. 重型构建的三条前置条件（血泪教训，必须同时满足）

`binary_freeze` 的每个 freeze 操作都要 `lease_from_watchdog()` 铸活体租约。连续失败三次才定位全：

1. **cwd 与模块 checkout 必须是同一个 checkout**（`runtime_bridge.py:354-359`）。
   → 在实现 worktree 内执行，且 `PYTHONPATH="$PWD/eval"`。
2. **build-lock 脚本必须是本 worktree 的**：`"$PWD/scripts/with-build-lock.sh"`，不能用主工作区的。
3. **`CARGO_TARGET_DIR` 必须事先存在**（`_optional_project_directory` 对它 `lstat()`，
   不存在报 `Cargo target root is unavailable`）→ 先 `mkdir -p`。

**绝不允许**设置 `RONDO_BUILD_WATCHDOG=0` 或任何放宽/关闭变量，也不得改用直接 Cargo 入口。
拿不到租约/cgroup/磁盘计数就 fail-closed 停下。

可用的完整命令模板：

## 6. 已经做完、不要重做的工程（七轮审查的实质产出）

- **门 1 判据已重建（workflow-v2）**：`code_mode_only` 下模型只发 `custom_tool_call(name=exec)`，
  团队工具全在 JS 里调，Responses 线上顶层 `function_call` 数为 0 —— 原 v1 判据结构上不可能通过。
  现读冻结二进制自身的 **rollout trace**（`CODEX_ROLLOUT_TRACE_ROOT`，产品既有能力，未改产品代码），
  只认 Rust dispatch 侧记录的工具名/namespace/参数/handler 返回值，并要求每条 dispatch 绑定回抓包里
  模型真实发出的 code cell。**不解析 JS、不采信 `custom_tool_call_output`**（两者模型都能伪造）。
  20 条对抗回归在 `eval/tests/test_multi_m5_trace_evidence.py`。
  团队工具的真实 namespace 是 **`collaboration`**（源码里 `ToolName::plain` 会误导，被 namespace override 包过）。
- **门 2 模型全链贯通**：锁里的 root/member 模型贯通 `TerminalBenchRequest → make_run_spec → adapter argv → proxy`，
  Docker 启动前 `require_pinned_model` 逐字段比对。宿主别名与全局 `AGENT_DEFAULT_SUBAGENT_MODEL` 保持 **sol**
  （翻成 terra 会静默改写本机每个 Multi campaign 的成员身份）。
- **$120 是数学上限**：冻结 token 信封（输入 272k / 输出 128k）在账本 settle 处强制，
  预留由价目表机械推导 `$2.22`，故 `charged ≤ reserved` 恒成立；每 run 上限由最大并发
  （Root+3 成员+Guardian = 5×预留）推导。
- **infra-taint 语义**：任何上游故障（保守结算 / operator-confirmed-unbilled）都给 run 打
  `infra_taint={count, first_reason}`，**与是否 stop 无关**。门 1 带 taint 一律 `infra_failed`
  （即使七谓词全真）；门 2 带 taint 一律 `counts_as_effective=false`，不进入退化判定。
  阈值只管"继续/停止"，不管"算不算证据"。
- **产品缺陷已修（本轮核心）**：`multidev/.../multi_agents_v2.rs::communication_from_tool_message()`
  把 code-mode 的 `spawn_agent` **明文** message 误包成 `encrypted_content`，成员请求因此被
  provider 拒成 `invalid_encrypted_content`——cm4 里成员 8 次推理 8 次全失败、Root 22 次 0 失败，
  成员从未完成一个回合。已让 `ToolCallSource::CodeMode` 走明文分支，**`Direct` 的 encrypted 语义保持不变**，
  5 条 Rust 回归在 `multi_agents_v2_tests.rs`（含反向验证：回退修复后 3 条 code-mode FAILED、2 条 Direct 仍 ok）。
