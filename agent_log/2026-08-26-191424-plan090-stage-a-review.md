## Findings

### High — 第二 seed 没有已绑定的随机自由度，却会被宣称为跨 seed 稳定性

`plan090_contract.py:105-108` 只改变 recipe 的整数 seed；底层 adapter 虽设置 Python/Torch/NumPy RNG（`plan082_adapter.py:258-267`），但正式更新固定按候选排序和既有 pair 顺序遍历（`plan082_adapter.py:493-545`），没有 shuffle。冻结模型配置的 `attention_dropout` 为 `0.0`，Transformers 4.52.3 的 `Qwen3ForSequenceClassification` 头也是直接线性 `score`，没有 sequence-classification dropout；因此当前实现没有证明 seed 会改变 Route O 的任何正式计算。现有 terminal 仍会把两条结果表述为 `route_o_confirmed_on_same_validation_two_seeds=true`，这会把一次确定性重复误写为跨 seed 稳定性，并可能为没有信息增量的第二条训练付费。

权威只读依据：

- [冻结模型 config（官方 Hugging Face）](https://huggingface.co/Skywork/Skywork-Reward-V2-Qwen3-1.7B/blob/e51ea3e08fb81326c3b812a7ff0cb9cee83e59cc/config.json)
- [Transformers 4.52.3 Qwen3 sequence-classification 实现](https://github.com/huggingface/transformers/blob/v4.52.3/src/transformers/models/qwen3/modeling_qwen3.py)

整改要求与审查决定：不要为了“制造 seed 差异”新增 dropout、随机数据选择或其它会改变 Route O 的训练路线。应在冻结合同、runtime/结果和测试中明确绑定真实 seed 语义：若没有 seed-sensitive consumer，第二条只能定义为使用不同 seed 元数据的独立 clean repeat，用于执行/数值重复性，必须把 `seed_sensitive_stability_tested` 记为 false，不得宣称排除了随机 seed 偶然性；PASS 结论相应降格为“两次 clean run 重复”，而不是随机 seed 稳定。仍按原顺序保留第二次 clean run，以满足最低重复性，不另建随机化设施。若执行者能以冻结模型和实际运行路径证明现有 Route O 确有 seed-sensitive consumer，可采用证据更强的等价方案，但不得改变 scope、objective、更新数或数据语义。

### Medium — base/旧 Route O no-update 诊断缺少 objective 分量

`plan090_cli.py:444-470` 的 `_diagnose` 只生成普通 train/validation observation，没有像正式 controller 一样附加 `objective_diagnostic`。因此阶段 B 首步无法按同一实现比较 exact base 与 Plan 087 Route O 的 weighted、binary、boundary、within-PASS objective，未满足本任务统一诊断要求。

窄修：复用现有 objective diagnostic 计算，给两类 no-update 诊断的 train 和 validation observation 加入同 schema 分量并做真实 receipt/identity 检查；补一个聚焦回归，验证 base 与 legacy 两个角色输出同口径 objective，且仍为 no-gradient/no-update。不要另建诊断 pipeline。

### Medium — task-root 写保护不确认 root 属于 Plan 090

`plan090_cli.py:794-817` 只验证输出位于调用者给定的 `RONDO_PLAN090_TASK_ROOT` 内；任意现存安全目录都可作为 root。虽然 bootstrap/launch shell 检查 `/workspace/rondo-plan090-*`，但并非所有 Python start/finalize/handoff 命令都由这些 shell 强制包裹。误把环境变量指向 Plan 082/087 root 时，当前门会接受在其中写入，违反历史 roots 只读和独立 namespace。

窄修：让两个 helper 复用一个 Plan 090 task-root validator，至少要求 resolved root basename 为非空 `rondo-plan090-*`；真实云端入口继续要求 `/workspace/rondo-plan090-*`，测试 fixture 使用同前缀。补接受 Plan 090、拒绝 Plan 087/任意 root 的聚焦测试。不需要通用 namespace/权限体系。

### Medium — 两条正向 BF16 后若恢复闭环遭基础设施故障，没有合法终态

PASS 要求第二 BF16 checkpoint 已 fresh-process recovery（`plan090_finalize.py:454-457`），但 `INCONCLUSIVE_INFRASTRUCTURE` 又无条件拒绝两条及以上 run（`plan090_finalize.py:402-408`）。因此两条 BF16 都形成有效正向结果、随后恢复或必要闭环因外部故障无法完成时，既不能 PASS，也不能 INCONCLUSIVE。

窄修：允许“已有结果全为非负、但必需恢复/闭环确因基础设施无法完成”的 INCONCLUSIVE；继续严格拒绝用 infrastructure 覆盖任一有效负面结果。用两条正向但第二条未 recovery 的 fixture 覆盖此分支，同时保留负面不可覆盖测试。
