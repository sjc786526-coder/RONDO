# Codex 0.147.0 基线升级与 P0 重新验收

## 范围与结论

- RONDO 产品源码从 Codex CLI `v0.146.1` 整体升级到官方 `rust-v0.147.0`，上游 commit
  `be6e8eac34711945bc47d57635f4759f20f08df9`。
- 官方 `Cargo.lock` 的 135 个 workspace package 从发布占位值 `0.0.0` 机械规范化为
  `0.147.0`；第三方依赖图未借机升级。规范化后 lock SHA-256：
  `bc4fe450de929afe82928734f860ca83e5f9dc5f9f1211b0974ea47b57af77ca`。
- P0 的配置覆盖、Guardian 审批证据捕获、轮次关联、原子私有落盘和 fail-closed 主体全部保留。
- **P0 在 0.147.0 上重新验收通过。** 全量 workspace 套件完整执行，但不是全绿：
  14,074 项中 13,998 passed、74 failed、2 timed out、23 skipped。失败逐项记录如下，不能表述为
  “全量测试通过”。
- 本轮没有调用真实模型 API、没有运行 Docker、没有 Bazel，也没有把 `E_final` 外发。

## 0.147.0 兼容适配

1. API-key Guardian 的 provider 默认模型已是 `gpt-5.6-luna`。S1 出站 wire test 改用非默认的
   `gpt-5.5`，并继续用非默认 `high` effort，避免 override 完全失效时测试仍误绿。
2. Luna 走 Responses Lite：`E_final` 保留真实 wire shape，测试同时接受标准 Responses 顶层
   `instructions` 和 Lite `input` 内 developer message 承载 policy 的形态。
3. `ResponseItem::FunctionCall` 新增 `encrypted_function_args`。P0 规范化明确剥离该
   provider-private 运输字段，并锁定幂等和 tool call/output 配对不变。
4. 上游把 execution-policy approval reason 贯穿到 Guardian；P0 不改写这部分 policy/prompt，
   证据快照会自然保留最终请求中的有效理由。

## 定向验收

以下均在唯一升级 worktree、唯一 target 下运行；所有重量级 Cargo 命令都经过机器级锁、独立 cgroup
和实时资源看门狗，期间主工作区及其他 worktree 没有第二路构建。

- `cargo fmt --all -- --check`：通过。
- `just fmt-check`：通过。
- `just fix -p codex-core`：通过，耗时约 2 分 33 秒，无额外源码改写。
- `just write-config-schema`：通过，生成后 schema 无差异。
- P0 精确回归集：8/8 passed。
- Guardian / auto-review 相关集：10/10 passed。
- config / schema 相关集：6/6 passed。
- `codex-core` 冷编译：通过，耗时约 3 分 09 秒。
- 第一次定向调用的过滤表达式不匹配任何测试，nextest 返回 4；该次只枚举了 0 项，明确不计为通过，
  随后改用精确过滤器完成上述有效验收。

全量中的
`session::tests::mcp_elicitation_reviewer_uses_latest_runtime_authority` 两轮各在 60 秒超时。一次脱离正式
环境变量的直接复跑因 Rust 测试线程栈过小而 stack overflow / SIGABRT，不构成有效复现；恢复项目正式
`RUST_MIN_STACK=8388608` 后单测 1/1 passed，耗时 47.102 秒。因此它归为全量并发/环境慢测，
不是 P0 终态回归。

## 全量结果与资源峰值

- nextest：14,074 run；13,998 passed（其中 6 slow）；74 failed；2 timed out；23 skipped；
  测试摘要用时 411.315 秒。
- 项目峰值：127,400,132,608 B；target 峰值：126,006,960,128 B。
- cgroup 总内存峰值：20,406,046,720 B；匿名+内核不可回收峰值：11,188,396,032 B。
- swap 峰值：379,203,584 B；宿主最低 `MemAvailable`：12,453,208 KiB。
- cgroup / 宿主 `full avg10` PSI 峰值：4.08% / 3.72%。
- `stop_reason=none`：磁盘、内存、swap 与 PSI 均未触发主动停机。
- 验收和失败冻结完成后，通过同一看门狗执行精确 `cargo clean --target-dir <本 worktree target>`，
  删除 97,186 个可再生成文件（Cargo 报告 126.1GiB）；项目占用降至 1,393,119,232 B。

全量摘要之后，`codex-external-agent-migration` 的网络超时留下了 366 个
`git ls-remote https://github.com/openai/plugins.git` 后代进程，仍处于本次精确 systemd scope 内并
占用约 17.6GB（主要为可回收文件缓存）。当场先冻结、再只杀该 scope，没有影响会话或其他 worktree。
看门狗随后增加“主命令退出后 5 秒残留宽限，超时精确清理 scope”逻辑；用后台 `sleep` 合成场景验证为
`cleanup_reason=residual_processes_after_command` 且保留主命令退出码。

## 76 个终态未通过项归因

与隔离纯上游 0.147.0 的 84 个终态未通过项比较：66 项共同、RONDO 本轮独有 10 项、纯上游独有
18 项。两边环境并不完全同构，因此“独有”只表示本轮测试清单差集，不等于 RONDO 代码引入。

| 分类 | 数量 | 失败内容与判断 |

## 复盘与后续边界

- P0 通过的依据是格式/修复、精确 P0、完整 Guardian/auto-review、config/schema 及正式环境下慢测
  的组合证据；不是把 76 个全量失败忽略掉。
- 76 项中没有 Guardian evidence、model/effort override 或证据关联/落盘的终态失败。
- 若以后专门收口全量绿，应先隔离 `/tmp` 项目标记、skills、代理与 release version fixture，再分别
  复核 realtime、shell 与 migration；不要在本次基线升级里顺手修改无关上游断言。
- 原始 full log、watchdog CSV/summary 与定向复跑数据保存在本 worktree 的 `.codex/`；纯上游原始证据
  保存在主项目 `.codex/build-study/0.147.0-upstream/`。两处均 git-ignored；远端交付以本日志的
  失败清单和摘要为准。
