## 阻断一（已修）：预算代理禁止并发 main 请求

第一次冒烟：Root 跑了 24 个请求、退出码 0，但七项协作谓词全 false、`TEAM_REPORT.md` 未生成。

追查发现成员 agent 状态是
`/root/worker → errored: {"error":{"code":"request_rejected"}}`。
起初怀疑中转站拒绝子智能体，但抓包显示 24 条全部同一个 session、上游全部 200 ——
**成员的请求根本没发出去**。根因在我们自己的代理：

`api_budget_proxy.py:1485` —— `"concurrent main requests are disabled"`。
Root 有在途预留时，第二个 `role=main` 请求直接被本地拒成 HTTP 400。
这是单智能体时代的假设，而 Multi 的前提恰恰是 Root 与成员并发。

**这会必然烧光门 1 全部三次尝试，且失败原因与产品无关。**

改法：`LoopbackResponsesProxy` 增加 `allow_concurrent_main`（默认 `False`，其它 campaign 行为不变），
只在 M-5 的三个代理构造点显式开启。放开的是顺序约束，不是记账 ——
并发的两个请求各自持有预留、共同受同一 cap 约束。三条回归钉住：默认仍拒绝、
开启后两笔预留都在账、三个构造点确实开启。

第二次冒烟验证：成员不再被拒，请求数 18 → 21，`request_rejected` 消失。

## 阻断二（未修，需决定）：判据认错了 wire 形状

即使成员正常，谓词也全为 false，因为**判据在找一种真实模型不会使用的调用形状**。

eval 固定 `features.code_mode_host=true`，于是模型看到的团队工具在 code-mode 里，
它的实际调用长这样：

```js
const r = await tools.collaboration__spawn_agent({task_name:"worker", ...});
const r = await tools.collaboration__wait_agent({timeout_ms:60000});
const r = await tools.collaboration__followup_task({target:"worker", ...});
```

在 Responses 线上是 `custom_tool_call`（`name="exec"`，工具名嵌在 JS 源码里），
返回是 `custom_tool_call_output`。而决策 020 冻结的采集口径是
`evidence_source.kind = "responses_function_call_outputs"`，只认
`function_call` + `name=team_inspect`。抓包实测：全程 `tools` 字段为 `None`、
`tools_count=0`、顶层 `function_call` 数量为 0。

阶段 A 曾"实测确认 wire 形状"，但那次是**直接注入**一个 function_call 验证工具可执行，
并没有验证真实模型会不会那样调。结论对，前提错。

**影响**：门 1 按当前冻结判据，在 `code_mode_host=true` 下不可能通过 —— 
模型协作得再好，判据也看不见。
