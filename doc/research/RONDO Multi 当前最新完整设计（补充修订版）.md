# RONDO Multi 当前最新完整设计

RONDO Multi 的总体目标，是在冻结 Codex 已有多智能体执行能力之上增加一个轻量但可靠的团队信息协作层，而不是重新设计 Agent execution plane。Codex 原生继续负责 thread、spawn/fork、并行 Agent、shared workspace、多 writer、wait/resume/interrupt、send_message、followup_task、pending input、工具执行、sandbox、审批、生命周期等实际执行机制；RONDO Multi 主要研究的问题是：多个拥有私有上下文和独立推理过程的 Agent，如何把真正值得团队持续知道的信息提升为一种 Harness 可维护、可追溯、不会因 context compaction 或模型遗忘而静默消失的团队世界状态，同时又不把所有 Agent 的 transcript、reasoning 和工具结果互相广播。整个系统因此形成一个“私有 Agent reasoning + Harness-owned shared reality + Root selective coordination”的结构：Agent 保持私有 thread、reasoning 和局部工具轨迹；Harness 保存确定性的原始事实索引和团队事件状态；Root 获得一个紧凑的全局世界视图，并负责决定是否查证、等待、路由信息、重新派工、spawn verifier、直接介入实现或做最终裁决。

RONDO Multi 首先区分“原始事实”和“模型语义”。Codex 已经掌握大量客观运行时信息，例如某个命令实际执行过、exit code 是什么、stdout/stderr 是什么、某个 patch 被应用、某个文件被读取、某个测试 PASS/FAIL、某个工具调用产生了什么结果等。这些原始 payload 不需要为了多智能体协作再复制一份完整数据库，而继续保存在原有 rollout/thread/tool state 中。RONDO 只增加一个轻量 Fact Index，为值得引用的原始 observation 分配稳定 Fact reference，并记录 producer、时间/顺序、命令或工具类型以及指向原始 rollout/tool result 的 locator等必要信息。Fact Index 只回答“这个 Harness 确实观察到的事实在哪里”，不回答“它现在意味着什么”或“它现在是否仍然适用”。Fact 永远是历史 observation，而不是可被简单标记为 valid/invalid 的当前真理：例如某次测试曾经 FAIL，后来代码修改后再次 PASS，旧 FAIL 仍然是真实历史事实，只是它是否还能代表当前 workspace，要由模型根据任务语义、后续修改和验证目的判断。Root 或 Agent 需要时可以沿 Fact reference 下钻读取原始结果或重新执行 fresh verification。Shared workspace 的原有 Codex 语义保持不变，RONDO 不额外制造严格 snapshot 假设；多个 writer 仍主要依靠 Root 的任务拆分、自然语言 ownership、及时的信息沟通和最终测试/审查协调。 第一版继续沿用这一原有机制，不额外引入 worktree、写入锁或新的 workspace coordination；更严格的 multi-writer 协调、隔离与集成机制明确列为后续独立探索方向，根据真实运行中的冲突与收益再决定是否引入。

在此基础上，RONDO Multi 的团队世界状态不再以“每个 Agent 的最新完整 Handoff 快照”为核心，而改为一个 Event-centric 的模型：**Team Event 是 World State 的基本语义单元，一个 Event 表示某个 Agent 按偏高召回率原则主动外部化的一件具体事项，包括可能影响他人的事项、自己的阶段性进展、重要决策等等；它是否实际值得团队持续知道、跟踪或协调，由 Root 在全局视角下判断。Event 中包含事实证据引用（见上一段）和 Event-centric Handoff，Handoff 是该 Event 某一阶段的语义信息，而不是整个 Agent 当前工作的完整总结。** Agent 在形成可命名的发现、状态变化、重要阶段、风险、未决问题、验证结果、计划变化或其他阶段性成果时，应当以偏高召回率、较细颗粒度并有节奏地主动创建或更新 Event；这里要求它判断的是“是否已经形成一段不应在自己中断、context compaction 或后续遗忘后消失的局部语义进展”，而不是预先判断这条信息是否会改变 Root 或 sibling 的行动。信息对团队的全局相关性、优先级、是否需要传播以及应采取什么行动，属于 Root 的判断。**Agent 仍然必须保留“不发布 Event”的认知自由：Fact 只是 Harness 观察到的客观执行结果，而“这些局部结果是否已经形成值得外部化保存的语义进展”属于模型判断，不能因为 Fact 存在就自动升级成 Event；低层工具流水、重复状态或尚未形成语义的局部噪声不需要机械汇报。** 是否已经形成应发布的局部语义检查点仍由 Agent model 判断，Harness 不根据工具轨迹自动推断“现在应该产生事件”，也不自动把若干 Fact 聚类成语义事件。Event 发布层总体采用 recall-first 的错误成本取舍：漏报可能使 Root 永远不知道该信息，多报通常只增加 Root 一次可处理的注意力成本；具体汇报颗粒度和频率作为工程参数在真实运行中调节。Harness 的职责是在 Agent 主动调用 Event/Handoff 能力以后机械地登记 Event、版本、Fact refs、 Handoff、状态和相关元数据，并在需要时唤醒 Root。

每一个 Team Event 拥有稳定的 Event ID，例如 E17；Event 可以包含多个 Version，例如 E17/V1、E17/V2、E17/V3。Event ID 表示“这是同一件团队事项”，Version 表示“这件事情在不同阶段产生的语义更新”。**Event identity 属于团队级 World State，而不是最初创建它的单个 Agent；最初创建者只是 `created_by`。Root 将某个 Event 显式 route 给另一个 Agent 后，目标 Agent 获得该 Event 的可见性，并可以针对同一 Event 发布新的 Version，因此同一 Event 的不同 Version 可以具有不同 author。后文所说的 producer，均指具体 Version 的 author/producer，而不是 Event 的全局 owner。** Version 是不可变的历史记录，每个 Version 主要包含：该阶段新增的 Event-centric Handoff、从上一个Event之后新产生的 Fact refs（即这个 Handoff 发布周期中新产生的客观事实索引）、producer 侧状态、Root 侧状态以及必要的时间和来源信息。Event-centric Handoff 的作用域被 Event ID 限定，因此不需要重复总结 Agent 的其他工作，也不需要把其他 Event 的长期未决事项不断 carry forward。例如 E17 是“loader compatibility 问题”，那么 E17/V2 只需要说明这个兼容性问题相比 V1 有什么新判断、新状态和新证据，不需要重新描述 Agent 同时维护的 Windows 初始化问题 E18。这样可以显著缩短 Handoff，降低一次 Handoff 聚合太多语义和证据的风险。

这里的 Version 编号首先只是同一 Event 内不可变条目的追加顺序和稳定历史身份。`V1 → V2 → V3` 只说明 Harness 依次登记了这些更新，不要求后一个作者已经看到全部前序 Version，也不隐含严格的因果继承、语义替代或线性文档修订关系。多个已经获得可见性的 Agent 可以从不同任务、不同角度，甚至围绕同一函数对各自工作的不同影响，在同一 Event identity 下追加 Version；模型根据自己的任务语义使用或忽略其中内容。只有 Handoff、producer_state 或显式 `superseded` 等信息，才表达更强的替代、关闭、修正或其他语义关系。

这里的“本 Handoff 发布周期新增 Fact refs”首先是一组机械的 observation provenance，而不是 Harness 已经做过语义筛选的精确 claim-to-evidence mapping：它只保证这些 Fact 是该 Agent 在发布当时实际可见、并在当前发布周期中新产生或新进入其可见范围的 observation reference；不保证每个 Fact 都与 Handoff 中的每项判断一一对应，也不保证它们构成该判断的完整证据集合。Harness 无法替模型判断语义相关性，而模型若要精确筛选又可能需要重新读取大量 Fact 历史，因此第一版不强制更细的语义绑定。中期可以考虑把这些新增 Fact 机械组织成发布周期 Fact Window，并把它作为软建议或上下文/索引优化：Harness 提供本周期窗口，模型可在必要时额外突出其中直接相关的 Fact；Fact Window 不是第一版必须的数据结构，也不是 Event/Handoff 发布成功的前置条件。

Agent 在出现与既有 Event 高度相关的新信息时，可以为同一 Event 创建新 Version。这里存在两种正常演化方式。第一种是替代式更新：新状态已经取代旧状态，例如 V1 是“怀疑 fallback 会影响 loader”，后来 V2 已经“确认 loader 确实受影响”，那么旧 V1 在 producer 侧可以进入终态，而 V2 成为新的 active Version；历史 V1 不被删除，而永久保留作为这条判断演化轨迹的一部分。第二种是追加式更新：新发现与原 Event 高度相关，但并没有解决或替代旧 Version，例如 V1 是“Windows path 尚未验证”，V2 又发现“Windows 初始化顺序可能造成另一种风险”，那么 V1 和 V2 都可以继续保持 active。换句话说，同一个 Event 内可以同时存在多个尚未结束的 Version；Event 是语义事项的共同身份，Version 是该事项演化过程中产生的阶段性信息单元。真正属于一个可以独立协调的新问题、新风险、新决定或新的团队事项，则创建新的 Event，而不是无限塞进旧 Event。对已经由 Root route 给其他 Agent 的 Event，其他获得可见性的 Agent 也可以在同一 Event identity 下发布自己的新 Version，而不需要为同一事项机械创建一份“自己的 Event”。如果两个 Agent 在彼此不可见、保持独立调查时各自发现了同一个现实问题，它们仍然可以先创建两个独立 Event；Harness 不自动做语义聚类或合并，后续是否让工作收敛到某一个 Event identity 由 Root 判断并显式 route。具体应该 new Event 还是 new Version，属于语义判断，继续交给 Agent model。

每个 Event Version 有两套完全解耦的生命周期状态。第一套属于该 Version 的 producer/author，即发布这个 Version 的智能体，用于表示“从这个 Agent 的角度，这个 Version 所描述的事项是否仍然需要继续保持注意”。最小状态可以采用 open / closed，并允许后续根据需求增加 superseded 等更精确的终态；其中 closed 表示该 Version 所代表的问题对 producer 来说已经结束，而 superseded 可以用于表达“旧信息已经被一个新 Version 替代”，以区别于“问题本身真正解决”。第二套属于 Root，用于表示“Root 对这个 Event Version 已经处理到什么程度”。当前可以采用 pending / tracking / resolved：pending 表示 Root 尚未显式处理这个版本；tracking 表示 Root 已经理解并做过判断，但主动要求它继续占据自己的当前注意列表，例如正在等待 sibling 的调查、后续验证或跨 Agent 协调结果；resolved 表示 Root 对这个 Version 当前已经完成了所需的协调判断，不需要继续显示在 Root 的活动世界视图中。这里的 resolved 是 Root attention/coordination lifecycle 的结束，不等价于 producer 所认为的问题已经解决。这里所谓 Version 是不可变历史记录，指的是 author、Handoff、Fact refs、创建顺序等 authored payload 不被原地重写；producer_state 与 root_state 是附着在该 Version identity 上的生命周期投影，可以按上述语义更新。上述两套标签/状态的单位是event+vision，即针对特定事件的特定版本，而不是针对一个事件整体。

Producer 和 Root 的状态彼此完全独立。Root 将某 Version 标记为 resolved，不会让它从该 Version producer 的 active list 中消失；只要 producer 仍然认为它 open，它在该 Agent 下一次调用 Event/Handoff 工具时仍然会再次显示，从而持续提醒模型这个事项尚未结束。反过来，producer 将自己发布的 Version 关闭，也不会让 Root 自动认为它已经解决；如果该 Version 对 Root 仍处于 pending 或 tracking，这一关闭状态会继续留在 Root 当前可见的 Event chain 中，Root 仍然有机会消费和判断。若 Root 已经将该旧 Version 标记为 resolved，producer 之后仅把它从 open 改为 closed 不会重新唤醒 Root，也不会让该 Event 重新进入 Root 的 Active World Index；如果确实出现值得 Root 再次知道的新状态、新证据或新判断，应当发布新的 Version，而不是只修改旧 Version 的 producer_state。每当任何已经获得该 Event 可见性和发布资格的 Agent 创建新的 Version 时，新 Version 对 Root 默认重新进入 pending，因此即使 Root 已经 resolved 了 E17/V1，后来 A 或被 Root route 过该 Event 的 B 发布 E17/V2，E17 都会重新进入 Root 的活动世界视图。这样解决了“Root 已经处理过旧状态，导致后续 Agent 更新无法重新获得 Root 注意力”的问题。**第一版不做自动 escalation：Harness 不判断 Root 是否错误，也不因为某个 producer 持续不同意就自动覆盖 Root 的 resolved；持续异议主要通过 producer/author 后续获得新证据并发布新 Version，再次把该 Event 带回 Root 注意范围。**

Event 对不同参与方是否显示，由可见性与这两套状态共同机械投影。对子智能体而言，它默认只能看到自己已经知道的 Event，以及 Root 显式 route 给它的 Event；在一个已经可见的 Event 内，Agent 可以读取完整 Version chain，但只维护自己发布 Version 的 producer_state，其他作者的 Version 作为只读的团队历史与当前信息存在。只要该 Agent 在某个 Event 中仍有自己 producer_state 未进入终态的 Version，或者 Root 当前已经把该 Event 显式 route 给它作为任务相关信息，这个 Event 就可以继续出现在该 Agent 的 active event list 中；具体 route 信息何时不再对目标 Agent active，第一版继续复用 Root 的任务与通信语义，不另造一套全局订阅机制。对 Root 而言，只要 Event 中仍存在 root_state 非 resolved 的 Version，它就继续出现在 Root 的活动世界索引中；只有 Root 已经显式解决该 Event 的所有 Version，它才从 Root 默认视图退出。因此，同一个 Event 可以同时包含“某个作者已经 closed 的 Version”和“另一个作者仍 open 的 Version”，也可以出现“所有当前 Version 都已被 Root resolved，但某个作者仍继续调查”的状态；后一种情况下，一旦任何有资格的 Agent 产生新 Version，新 Version 又会自动让 Root 重新看到该 Event。只有当 Event 的所有 Version 对各自 producer/author 都进入终态，并且 Root 对所有 Version 都进入 resolved，该 Event 才完全退出当前注意力视图，成为 historical-only Event，但其 Event、Version、Handoff 和 Fact refs 永远保留在历史 World State 中。若 producer 已经终止或不可用而某个 Version 仍然 open，则按后文的 orphan 处置规则由 Root 显式关闭后，才可视为 producer 侧进入终态；后续如有需要，可以再细分 `retired` 等终态。

RONDO 为子智能体提供一个显式的 Event/Handoff 工具或 typed capability。Agent 调用它时，Harness 首先向模型展示该 Agent 当前所有有可见性、仍然 active 的 Events 以及其中相关的未终态 Version，让模型不能只依赖 conversation memory 记住这些事项。Event/Handoff 能力的系统提示同时持续提醒 Agent 按上述高召回原则，在形成阶段性语义检查点时主动调用，而不是只在最终完成时汇报；但 Harness 不按固定工具调用次数、固定时间间隔或单个 Fact 的出现机械触发 Event。**模型只需要对本轮状态或语义真正发生变化的 Event/Version 显式提交更新，例如关闭或标记自己某个 Version 为 superseded、为既有 Event 创建新 Version、创建全新 Event 等；未提及的 active Event/Version 默认保持原状态，不要求每次调用都机械提交 `keep_open`。** 这样，一个已经进入团队状态的重要事项不能仅仅因为模型下一轮忘记复述就静默死亡；Harness 不替模型判断它是否已经解决，但会在每次 Event/Handoff tool invocation 时重新把仍然 active 的事项带回模型注意力。正常情况下工具只展示 active Events，从而保持上下文紧凑；同时必须提供查看历史的能力——比如另外一个参数，例如通过 `include_closed=true`、`show_event_history()` 或类似参数，让 Agent 随时调取自己有权访问、但已经完全退出当前 active 视图的历史 Event 和 Version。当一个旧问题后来重新变得相关时，不修改旧历史 Version，而是在原 Event 下追加一个新的 Version，例如 E17/V4，并说明它因为新的证据或变化重新进入 active 状态。这样历史始终 append-oriented，可追溯且不会被重写。

Root 同样拥有针对 Team Event 的显式消费能力。Root 在每次模型采样时获得的是一个由 Harness 根据最新 World State 动态生成的 **Active World Index**，而不是 FIFO 队列，也不是完整历史 transcript。Root 会同时看到所有当前对自己仍然 active 的 Events，因此可以根据任务语义自由判断哪个事件更值得立即关注，而不受先进先出顺序约束。Active World Index 的基本单位是 Event，而不是 Agent；Event 不从属于某个 producer，Agent 作为各个 Version 的 author/producer metadata 出现。每个活动 Event 默认向 Root 提供这个 Event 的完整 Version chain，包括各 Version 的 Event-centric Handoff、Fact references、producer 状态和 Root 状态，使 Root 能看到这个事项从最初发现、后续确认、修正、实现、验证到关闭的完整语义轨迹和证据轨迹。例如 E17/V1 提供初始失败证据，V2 提供根因确认的新证据，V3 提供修复后的测试结果，Root 在消费 V3 时仍能看到 V1/V2 的旧语义和证据引用，因此不会因为每次 Version 只携带“自上次发布以来的新证据”而丢失完整来龙去脉。**这里第一版故意保留完整 chain：每个 Version 的 Fact refs 只覆盖该 Handoff 发布周期中新产生、并且该 Version 作者当时实际可见的证据，不能假定后一个 Version 会重新携带或覆盖此前证据；如果隐藏旧 Version，可能直接切断语义演化与证据来源之间的对应关系。是否以后增加 Event head、materialized projection 或其他压缩方式，属于真实运行后再根据上下文成本优化的问题。** **第一版的原则是先保证 canonical world projection 完整正确；只有真实运行证明 context 成本确实成为瓶颈后，才研究 materialized head / history folding，而不提前优化尚未证明存在的问题。** Fact payload 本身仍然不复制到 World State，Root 需要时才沿 Fact refs 下钻原始 rollout/tool result。

Root 对每个 Version 显式维护 pending / tracking / resolved 等自己的 attention state。Root 可以仅阅读后标记 resolved，也可以因为事件仍需要以后继续关注而置为 tracking；Root 的 attention state 可以附带极短的 Root-owned note，例如 `tracking_reason`、`awaiting`、`resolution_reason` 或 `route_purpose`，并可在确有需要时增加少量标签种类，用于跨 compaction 保留 Root 的协调理由，但这些 note 不自动成为团队语义。Root 是否调用工具、验证证据、route 给 sibling、spawn verifier、等待其他 Agent、重新拆任务、直接修改代码或什么都不做，仍然是 Root model 的语义决策。Root resolved 一个事件并不意味着删除历史，只意味着它不再占据当前 Root attention。当任何已经获得该 Event 可见性和发布资格的 Agent 以后追加新 Version，该 Event 都会重新进入 Root 当前视图。Root 同样应该能够主动下钻历史，例如 `read_event(E17)` 查看某个 Event 的完整 Version history，也可以按 producer 查询某个 Agent 历史发布过的全部 Event，包括已经完全关闭、已经从当前世界索引退出的事项。这样 Root 的默认上下文保持紧凑，但历史永远可恢复。

World State 是 Harness 在 Root conversation 之外维护的团队级状态，不依赖 Root 自己的语言历史，因此 Root context 即使发生 compaction，Team Event、Version、Fact refs 和双方 lifecycle state 也不会消失。第一阶段可以采用 session/team-scoped 的内存结构，重点解决“团队状态与模型 context 解耦”，而不必把持久化恢复作为初版核心问题。原始工具结果和 transcript 的 canonical payload 仍然由 Codex 原有 rollout/thread 设施保存，World State 保存的是 Event、Version、Event-centric Handoff、Fact references、双侧状态和必要索引，以及其他必要元信息。Root 每次 sampling boundary 都从当前 World State 重新生成 Active World Index，而不是把世界索引作为普通历史消息不断 append 到 conversation。World State 可以保留全部 Event/Version 历史，而 Active World Index 只投影当前仍需要 Root 注意的 Events，所以历史长度不会直接转化成 Root context 长度。Active World Index是和可压缩的消息上下文并列的，而不是其中的一部分，他又harness构造并且直接进入最终发送给model的消息，不会受到来回消息的累加或者上下文压缩的影响，类似系统提示词那样的存在（不完全相同）

Team Event 也是 RONDO 特有的 Root wake source。普通 tool call、read、patch、test 等只产生原始执行事实和必要 Fact refs，并不会因为每次工具执行都打断 Root。只有 Agent 按上述高召回、阶段性汇报原则主动创建或更新 Team Event 时，Harness 才将这次语义发布登记进 World State。若 Root 正明确处于 team/coordination wait，新的 Event 或 Version 可以唤醒 Root，使其重新获得调度决策机会；若 Root 此时正在进行 model sampling 或工具执行，则不强行中断当前动作，新变化进入 World State，并在下一个 sampling boundary 通过最新 Active World Index 出现。Wake 只意味着 Root 获得重新协调的机会，不意味着自动广播、自动 steer、自动 spawn 或自动执行任何动作。唤醒root之后，root仍然看到的是最新 Active World Index而不是只有最新事件。

Sibling 之间的信息传播继续由 Root 选择性决定。Children 默认不会获得完整 Team World State，也不会因为某个 Agent 发布 Event 就自动接收 sibling 的语义判断。**Root 对正式 Team Event 的转发以 Event 为单位，而不是把同一事项拆成彼此失去身份关联的零散版本消息：Root 阅读 Event 后，可以根据任务相关性、独立调查价值、当前执行阶段和其他语义因素，决定是否把某个 Event 显式 route 给特定 sibling；目标 Agent 因而获得该 Event identity、当前完整 Version chain、相关 Fact references，并可在后续针对同一 Event 发布自己的 Version。** Root 自己整理的补充任务、局部说明或不需要进入 Team World State 的普通信息仍然可以直接发送，而不要求先创建 Event。实际通信继续复用 Codex 原有 `send_message`、`followup_task`、pending input 等执行机制。这样既能复用客观取证、减少重复工具调用，也保留各 Agent 的 reasoning independence；例如 Root 如果有意让两个 Agent 独立调查同一个问题，可以暂时不向 B 透露 A 的判断，而不需要 Harness 新增特殊的“blind mode”。Agent 创建时通过 fork 继承多少 parent context，仍然负责 initial epistemic inheritance；Agent 创建以后 Root 是否把新产生的 sibling Event/Facts 告诉它，则负责 subsequent collaborative visibility，这两个维度继续独立。Root 在派任务时还可以通过自然语言 task specification 提供一份轻量 notification contract，明确哪些类型的变化尤其值得尽快发布 Event；这只是提示词/任务说明层的引导，不改变“是否已经形成应发布的局部语义检查点仍由实际工作的 Agent 判断，而其全局相关性、优先级和路由仍由 Root 判断”的原则。

Root 的定位仍然是偏 Scheduler、Information Router 和 Trusted Arbiter，而不是被硬性限制为纯 supervisor。Root 主要利用 Active World Index 判断当前团队状态、哪些 Event 值得优先处理、是否需要改变任务拆分、是否需要传播信息、是否需要验证冲突、是否应该继续等待等；但 Root 保留完整 Agent 能力，在重要分歧、证据不足、最终裁决或直接介入更划算时，可以自己读源码、调用工具、跑测试、修改代码和完成最终实现。Root 也拥有与其他 Agent 相同的 Event/Handoff 能力，可以主动创建 Team Event、在可见 Event 下发布 Version、维护自己作为 producer 的状态，并按需 route 给子智能体；不需要另设特殊的 Root Event 类型。Root 自己执行工具得到的 observation 与 child Fact 没有本质区别，同样可以进入 Fact Index，并在必要时成为团队事件的证据来源。例如有的事件，root自己查证可能更快。当前体系不依赖固定的模型强弱身份、信誉权重或多数投票，也不预设固定 reviewer/verifier 流程；模型和角色按任务需要分配，协作中的共同锚点主要是可追溯的 Harness observation，而 observation 的现实含义仍由 Agent/Root 结合上下文作语义判断。

Active World Index 现在以“仍值得 Root 注意的 Events”为主体，因此 Agent population 本身不再导致世界索引无限增长。Agent completion 是 Codex lifecycle 事实，不会自动删除其 Event；一个已经结束的 Agent 所留下的重要发现仍然可以继续出现在 Root 世界索引中，只要相关 Version 还处于 pending/tracking。反过来，一个仍然活跃的 Agent如果当前所有 Event 都已经被 Root resolved，也无需因为这个 Agent 仍存在就持续占据一块 Root context。随着 producer 和 Root 分别显式结束各自的 Version 状态，Event 自然转入 historical-only，因此世界索引规模主要由“当前仍有注意力价值的团队事项数量”决定，而不是由任务已经运行了多久、曾经 spawn 过多少 Agent 或产生了多少历史工具调用决定。另外智能体的结束、运行、等待等宏观 lifecycle 状态在现有 codex 的多智能体控制与沟通体系里面已经有对应机制，可以直接复用，而不必作为单独的特殊事件类型，也不在第一版另建一套 Execution State / Execution Index；例如 Root 的协调等待继续依赖现有 `wait_agent` / mailbox activity / agent status 变化的唤醒语义。

如果某个 Version 的 producer 已正常结束、被 interrupt、崩溃或因其他原因不可用，而 producer_state 仍为 open，Harness 不自动把该 Version 视为 closed，而保留原状态并附加 producer lifecycle metadata，明确作者已经终止或不可用。Root 在必要时可以对这类 orphan Version 执行显式关闭，使其退出当前注意力投影；该动作应明确记录为 Root override 及其理由，而不伪装成原 producer 自己作出的关闭。后续如果真实运行需要区分“作者关闭”和“协调者终结”，可以再增加 `retired` 等终态；第一版不为此建立复杂 ownership transfer。

第一版预期团队规模为 2–8 个 Agent，实际通常更少，目标是先稳定跑通上述 World State、阶段性汇报和 Root 调度语义；暂不为几十或上百 Agent 提前引入层级 coordinator、topic subscription、复杂聚合或 learned routing。

整个设计最终可以抽象为一条统一的信息流：Agent 在私有上下文中进行大量探索、推理、工具调用和局部实现；Harness 把其中客观执行结果保存在原始 rollout/thread，并通过 Fact Index提供稳定引用；当 Agent 自己判断形成一个应当外部化保存的阶段性语义事项时，它创建 Team Event E，并发布 V1，其中包含 Event-centric Handoff 和新 Fact refs；Event identity 从创建时起属于团队级 World State，最初 Agent 只是 V1 的 author/producer；以后同一事项发生变化时，原作者或被 Root 显式 route 该 Event 的其他 Agent 都可以创建 V2/V3 等新 Version，并分别维护自己发布 Version 的 producer 状态；Harness 在每次 Event/Handoff tool invocation 时把该 Agent 当前有可见性且仍 active 的 Events 再次显示给它，防止模型因遗忘让重要状态静默消失，而未被模型显式更新的 Event/Version 默认保持原状态；Root 则看到所有自己尚未 resolved 的 Team Events及其完整版本链，对每个 Version 显式标记 pending、tracking、resolved等状态，并根据语义自行决定查证、传播、等待、调度、实现或裁决；Root resolved 不影响各 Version producer 的视图，producer closed 也不替 Root 自动完成消费；如果任何有资格的 Agent 后续产生新 Version，Event 会重新获得 Root attention；只有所有 Version 对各自 producer/author 都进入终态（或 orphan Version 已由 Root 显式关闭）并且 Root 对这些 Version 都进入 resolved，Event 才从当前视图退出，但全部历史和 Fact provenance 始终可以查询。

因此，RONDO Multi 当前的核心不是“所有 Agent 共享上下文”，也不是“把多智能体变成一个聊天群”，而是建立一个 **Event-centric、evidence-backed、dual-lifecycle、Harness-owned Team World State**：事实由 Harness 保存和定位，语义由实际工作的 Agent 按偏高召回率原则自主决定是否形成并发布局部语义检查点，而信息的全局相关性、优先级和传播由 Root 判断；每一件值得团队持续记住的事情获得稳定、team-owned 的 Event identity，最初创建者只是该 Event 的 `created_by`，被 Root 显式 route 后不同 Agent 可以在同一 Event 下贡献各自不可变的 Version；每个 Version携带该发布周期新增的 Fact provenance 和紧凑语义说明，并由自己的 producer/author 与 Root 分别维护相互独立的注意力生命周期；重要状态不会靠模型遗忘自然消失，但未发生变化的 active Event 也无需被模型机械重复提交；Root 始终看到完整但有界的活动事件世界，并自行决定哪些信息应该影响其他 Agent。这样既保持多智能体上下文和推理的独立性，又让客观证据、阶段性判断、风险、验证和跨 Agent 影响可以成为可追溯、可更新、可显式消费的团队共同现实。

RONDO Multi 的第一版定位首先是工程实践、Harness 创新与技术训练，而不是以学术论文式的单一性能胜负作为存在前提。任务成功率、成本、重复工具调用、Event 负担等测量仍用于暴露问题和驱动迭代，但不作为一开始的 kill gate；只要系统能够实际运行、边界清楚、状态可追溯，并让上述协作语义进入真实工程实践，即使暂时没有超过原生 Codex Multi-Agent，也仍然具有项目价值。

关于复用codex现有的智能体通信机制，我的看法是：

1. RONDO 不新建独立的 Agent-to-Agent 传输协议：Root 向 sibling 正式转发 Team Event 时以 Event 为单位，连同该 Event identity、当前 Version chain 与相关 Fact refs 继续复用 Codex V2 的 `send_message` / `InterAgentCommunication` 投递；普通补充任务或局部信息仍可作为普通消息追加。需要触发目标 Agent 新一轮执行时，则复用带 `trigger_turn` 语义的 `followup_task`，从而沿用现有 `AgentControl → target Session mailbox` 通路。`followup_task` 不只适用于 idle Agent；若目标仍在运行，也继续沿 Codex 原有机制投递。

2. 对仍在运行的 Agent，新的团队信息不启动特殊“上下文同步”流程，而继续进入其现有 mailbox / pending-input 流程，并在 Codex 原有允许追加输入的安全注入边界进入目标 Agent 的模型上下文，使 RONDO selective steering 与 Codex V2 既有的途中追加输入语义保持一致。

3. Root 的协调等待直接扩展现有 `wait_agent` 机制：当前 V2 `wait_agent` 已通过 `InputQueueActivity` 等待 mailbox activity、steered input 或 timeout；RONDO 只需把新的 Team Event/Version 发布纳入同一 coordination-activity / wake 通路，使 Root 在明确处于 team wait 时能因 Team World State 发生变化而立即重新获得调度机会，而无需另建轮询线程。

4. Event wake 只负责通知 Root“团队世界发生了变化”，不把 Event 正文作为普通消息持续 append 到 Root conversation history。Root 被唤醒或进入下一次 model-request boundary 时，Harness 根据当前 Team World State 重新生成最新 Active World Index；因此一次 wake 可以自然合并等待期间产生的多个 Event/Version 更新，且 Root conversation compaction 不影响团队状态。

5. Agent 的 spawn/fork、completion、wait、resume、interrupt、list/status 等生命周期继续复用 Codex 原有 multi-agent control plane。RONDO 的 Team Event、Event-centric Handoff、Fact Index 和双侧 attention state 只是其上层的信息协作机制，不复制 Agent mailbox、registry、task scheduler 或 lifecycle system；新增改动集中在“什么信息进入 Team World State、Team World State 的变化何时唤醒 Root、Root 选择向谁传播哪些信息，以及每次 Root sampling 如何动态投影 Active World Index”这些问题上。
